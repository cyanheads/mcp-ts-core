# 0.10.17 — 2026-07-26

## Added

- **`CANVAS_TEMP_PATH`** (`canvas.tempRootPath`) — scratch root for DuckDB's `temp_directory` plus the transient files behind stream exports and the spillover round-trip. Defaults to `<os.tmpdir()>/mcp-canvas`, created on first use. Distinct from `CANVAS_EXPORT_PATH`, which keeps user-requested export files where the caller asked for them. [#292](https://github.com/cyanheads/mcp-ts-core/issues/292)

## Changed

- **`scripts/clean-mcpb.ts`** strips a second entry class after `mcpb pack` — `node_modules/@duckdb/node-bindings-*` platform slices, alongside the dependency-shipped agent docs it already removed. `lint-packaging`'s check 8 verifies both classes and reports them as separate errors; a unit test pins the two `NATIVE_BINDING_ENTRY` patterns identical. [#274](https://github.com/cyanheads/mcp-ts-core/issues/274)
- **Skills:** `api-canvas` 1.9 → 2.0 (`CANVAS_TEMP_PATH` row, scratch-root wording), `api-config` 1.8 → 1.9 (`CANVAS_TEMP_PATH` row), `field-test` 2.7 → 2.8 (configurable `mcp_start` timeout with early-exit detection, negotiated protocol version surfaced by `mcp_init`, `mcp_call` fails loudly on transport errors and emits only the reply, `mcp_stop` takes the port and kills the port-holding child, truncation-retrievability test category).

## Fixed

- **`fetchWithTimeout` timeouts classify as `Timeout` (-32004) again** — the timeout now aborts with a `TimeoutError` `DOMException` instead of the string `'FETCH_TIMEOUT'`, and classification identity-matches that instance against `controller.signal.reason` outside any `instanceof Error` gate. `fetch` rejects with the abort reason *value*, so a string reason fell through to the generic network wrapper and surfaced as `ServiceUnavailable` with `errorSource: FetchNetworkErrorWrapper`. Identity matching also keeps a caller that aborts with its own `TimeoutError` classified as `FetchAborted`. [#289](https://github.com/cyanheads/mcp-ts-core/issues/289)
- **Logger rate-limit bookkeeping evicts on every runtime** — the `setInterval` armed only outside serverless is replaced by a traffic-driven sweep, so `messageCounts` is bounded and the "suppressed N times" record is emitted in a Worker isolate, which has no timer and no `close()`. A `MAX_TRACKED_LOG_KEYS` cap of 1000 drops the oldest entries when a high-cardinality burst outruns window expiry inside a single window. [#277](https://github.com/cyanheads/mcp-ts-core/issues/277)
- **DuckDB scratch I/O no longer lands in the process cwd** — `DuckdbProvider` sets `temp_directory` at instance creation and routes stream-export and `importFrom` temp files to the same root. DuckDB defaults an in-memory database's `temp_directory` to a cwd-relative `.tmp`, so the first query to exceed `memory_limit` failed with `Permission denied` under a non-root or read-only container rootfs. [#292](https://github.com/cyanheads/mcp-ts-core/issues/292)
- **Task bookkeeping expires with the tasks it describes** — `SessionAwareTaskStore` records each ownership row's deadline from the task's TTL, prunes lazily on read, sweeps on creation, and refreshes on `storeTaskResult` / terminal `updateTaskStatus` to track the inner store's timer reset. Previously nothing ever deleted a row, so every task call under HTTP added a permanent entry. An expired row now falls through to the inner store's not-found instead of a `Forbidden` that confirmed the id had existed. [#276](https://github.com/cyanheads/mcp-ts-core/issues/276)
- **Abandoned task message queues are reclaimed** — `TaskManager` wraps the SDK's `InMemoryTaskMessageQueue` in an `EvictingTaskMessageQueue` bounded by the same TTL the task store applies (`config.tasks.defaultTtlMs`, else the shared `DEFAULT_AUTO_TASK_TTL_MS` of 120 s). The SDK deletes a queue only in `dequeueAll`, so a client that never fetched a result and never cancelled stranded that queue for the life of the process. Eviction is lazy and traffic-driven — no per-task timers. [#276](https://github.com/cyanheads/mcp-ts-core/issues/276)
- **`.mcpb` bundles are portable again** — `mcpb pack` archives the whole project directory, so a DataCanvas server's bundle carried the build host's `libduckdb` slice: ~39 MB, Apple-Silicon-only, over the 25 MB cap registries enforce. `@duckdb/node-api` is an optional peer loaded through `lazyImport`, so a bundle without the native runs every non-canvas tool normally and canvas tools return the install hint. [#274](https://github.com/cyanheads/mcp-ts-core/issues/274)
