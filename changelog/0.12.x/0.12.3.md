# 0.12.3 — 2026-08-21

## Changed

- **Bun pins move to `1.4.0`** ([#361](https://github.com/cyanheads/mcp-ts-core/issues/361)) — both stages of `Dockerfile` and `templates/Dockerfile`, plus `packageManager` in `package.json` and `templates/package.json`. `engines.bun` stays `>=1.3.0`; `@types/bun` and `bun-types` stay `^1.3.14`, whose caret already resolves 1.4.x.
- **`mcp.tool.duration` / `mcp.resource.duration` cover the response pipeline, not the handler alone** ([#346](https://github.com/cyanheads/mcp-ts-core/issues/346)) — an expensive `format()` or enrichment merge now lands in the histogram. `output_bytes` is unchanged: it measures the handler's returned domain value.
- `package.json` `description` matches the README tagline.
- Shipped skills: `api-config` 1.13, `api-telemetry` 1.7.

## Fixed

- **A failure after the handler returns is recorded as a failed call** ([#346](https://github.com/cyanheads/mcp-ts-core/issues/346)) — output-schema validation, `format()`, the enrichment merge, and the trailer render moved inside the measured region, so a failure in any of them produces an ERROR span, `success=false` counters, an error-counter increment, and `isSuccess: false` in the completion log.
- **Stdin EOF runs the shutdown path a signal runs, then exits explicitly** ([#322](https://github.com/cyanheads/mcp-ts-core/issues/322)) — the stdio transport watches `process.stdin` for the client hanging up, so the OTel export leaves the process and a handle a service registered without `unref()` can no longer keep the server resident after its client is gone.
- **`Logger.close()` bounds each pino flush at 2s** ([#342](https://github.com/cyanheads/mcp-ts-core/issues/342)) — a completing callback is still awaited in full; a runtime whose callback never arrives (workerd) releases the shutdown path instead of hanging it.
- **An async HTTP bind failure reaches the retry ladder instead of crashing after a success log** ([#315](https://github.com/cyanheads/mcp-ts-core/issues/315)) — the bind attaches its own `'error'` listener and resolves only on a confirmed `'listening'`. `EACCES` and `EADDRNOTAVAIL` reject immediately with the OS error as `cause`; every other code retries.
